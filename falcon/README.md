# falcon

The Novint Falcon as a backend for [robot-control](../robot-control): a 3-DOF
haptic device driven over ROS 2, with CHAI3D rendering the scenes the hand
feels. **The abstractions are not here** — this repository extends them.

One repository per robot, and this one is the Falcon. It installs as the
distribution `falcon-robot`, whose module is `falcon_robot` --- the same rule
`robot-control` follows, hyphens outside and underscores inside. The module is
deliberately *not* named after the repository directory: a package that shares
its parent's name is shadowed by that directory whenever the parent is on the
import path, which silently hides `spec.yaml`. Another robot ships from its own
repository under its own name, and the two coexist without either knowing about
the other.

```
falcon_robot/               the robot's package: `import falcon_robot`
├── spec.yaml               parameters, bounds, rate caps, screen_axes, and the
│                           device's rated maxima — declared once, read by the
│                           Python side rather than repeated there
├── spec.py                 loads spec.yaml (pure, no ROS)
├── backend.py              rclpy bridge; declares BACKEND
├── exercises/              one folder per exercise, with this device's own bounds
│   ├── reach/              reach.py  game.py  reach.yaml
│   │                       window.py       the 2D window and its ROS link
│   │                       run_window.sh   opens it (this exercise's viewer)
│   └── haptic_rendering/   render.py  render.yaml  scene.py  geometry.py
│                           viewer.py  marker_geometry.py  falcon_haptic.rviz
│                           run_rviz.sh     opens RViz (this exercise's viewer)
├── ros2_ws/                ROS 2 colcon workspace. Only src/ is versioned;
│   │                       build/, install/ and log/ are colcon's output and
│   │                       are regenerated by `colcon build`.
│   └── src/falcon_ros2/
│       ├── src/falcon_haptic_node.*    device I/O + 1 kHz control loop (owns the USB device)
│       ├── src/haptic_renderer.*       CHAI3D finger-proxy scene renderer
│       ├── msg/                        DeviceState, ForceCommand, HapticObject, HapticScene
│       └── launch/
└── scripts/                robot-wide, not owned by any exercise:
                            run_mcp.sh      what an MCP client starts
                            run_node.sh     owns the USB device
                            _python.sh      resolves an interpreter, sourced by
                                            every launcher
```

## ROS 2, briefly

ROS is not an operating system. It is a library and a set of conventions for
letting **separate processes exchange typed messages**, with tooling to watch
that traffic while it runs. It is here because this device is driven by two
processes in two languages — a C++ node holding the hardware and a Python
backend above it, for the reason the next section gives — and something has to
carry floats between them a thousand times a second.

Four terms cover everything this repository uses.

**Node** — a process with a name. Four exist here: `falcon_haptic` (C++, owns
the device), `falcon_mcp_backend` (`backend.py`), and one per viewer,
`haptic_viz` and `exercise_window`. `rclcpp` and `rclpy` are the same client
library in C++ and in Python.

**Topic** — a named, typed, one-way bus. A publisher does not know who is
listening, or whether anyone is, and any number of nodes may publish or
subscribe. That anonymity is what lets a viewer be opened and closed
mid-session without reconfiguring anything — and it is why a topic with no
subscriber is silence rather than an error.

**Message** — a schema. The files under `msg/` are flat lists of typed fields,
and the build generates a C++ header and a Python class from each. That is why
`from falcon_ros2.msg import ForceCommand` resolves with no such file in the
tree, and why changing a `.msg` means rebuilding both sides.

**QoS** — a per-endpoint delivery policy, and the one that bites. A subscriber
whose profile is incompatible with the publisher's receives **nothing, with no
error**. The default on both sides is `RELIABLE`, so a subscriber that takes the
default on a `BEST_EFFORT` topic looks exactly like a dead device. Every
endpoint here therefore states its profile outright:

| Topic | Direction | QoS |
|---|---|---|
| `/force_command` | backend → node | best-effort, volatile, depth 1 |
| `/device_state` | node → backend, viewers | best-effort, volatile, depth 1 |
| `/haptic_scene` | backend → node, viewer | reliable, transient-local |
| `/exercise_view` | backend → window | reliable, transient-local |
| `/haptic_markers` | viewer → RViz | default; display only |

Choosing between them is one question: **is this a signal or a fact?** A
kilohertz stream is a signal — only the newest sample matters, and a
retransmitted stale force is worse than a dropped one. A scene is a fact, so it
is latched (`transient-local`) and a viewer opened later still receives the
current one instead of waiting for a change.

Nothing here uses ROS services, actions or tf. Request/response is MCP's job,
long-running goals are the exercise contract's, and device coordinates are
world coordinates — the single static transform exists only because RViz
insists on a frame to anchor to.

### Building the workspace

`colcon` is ROS 2's build tool, and it is a *meta*-build tool: it scans `src/`
for packages, orders them by their declared dependencies, then invokes each
one's own build system. `package.xml` here declares `ament_cmake`, so for this
package colcon ends up running CMake. It is run from the workspace root — not
from `src/`, and not from inside the package:

```bash
source /opt/ros/jazzy/setup.bash            # before building, not after
cd falcon_robot/ros2_ws && colcon build
```

ROS has to be sourced *first*, because the `find_package(rclcpp)` calls in
`CMakeLists.txt` resolve against it. Three directories come out, none of them
versioned:

| | |
|---|---|
| `build/` | per-package intermediate objects and the CMake cache |
| `install/` | the result, and the only one anything else reads |
| `log/` | one subdirectory per invocation, with the full output |

For this package the build does two jobs. It compiles `falcon_haptic_node`
against the Force Dimension SDK and CHAI3D, and it runs `rosidl` code
generation over the four files in `msg/`, emitting both C++ headers and the
Python module `falcon_ros2.msg`. The second job is what makes `backend.py`'s
import work: the messages are a **build product**, so editing a `.msg` is a
rebuild for both languages.

Two consequences worth knowing, because neither announces itself:

- **An already-sourced shell keeps the old `install/`.** It does not follow a
  rebuild, so a newly added message stays invisible until that shell sources
  `install/setup.bash` again.
- **A running node keeps executing the old binary.** Building restarts nothing;
  see [Running](#running).

`--packages-select falcon_ros2` rebuilds this package alone. If a build begins
failing in ways that make no sense, delete `build/ install/ log/` and build
again — colcon caches CMake configuration, and a stale cache outlives the
source change that invalidated it.

### Entering the environment

ROS is a shell environment, not a pip package. Two `source` lines put it on the
path, the distribution and then this workspace:

```bash
source /opt/ros/jazzy/setup.bash
source falcon_robot/ros2_ws/install/setup.bash
```

They mutate the shell, so every new terminal needs them again and **a process
spawned with a clean environment inherits neither** — which is what the
launchers in `scripts/` exist for. `rclpy` comes from the system ROS install
rather than from pip, so a virtualenv hides it unless created with
`--system-site-packages`.

### Looking at a running system

Because topics are named and typed, the traffic can be inspected from outside
without touching the code:

```bash
ros2 node list                     # who is running
ros2 topic info -v /device_state   # endpoints and their QoS
ros2 topic hz   /device_state --qos-reliability best_effort
ros2 topic echo /device_state --qos-reliability best_effort
ros2 param get  /falcon_haptic max_force_n
```

The `--qos-*` flags are not optional: the CLI takes the same `RELIABLE` default
as everything else, so without them it prints nothing on these topics. For
`/haptic_scene`, pass `--qos-durability transient_local` instead.
`ros2 topic info -v` is the tool for the silence case — it prints each
endpoint's profile, so a mismatch becomes visible rather than mysterious.

## The C++ side

Everything under `ros2_ws/src/falcon_ros2/` is C++ for one reason: the device
runs a control loop at about a kilohertz, and a Python process cannot hold that
rate — nor can it be relied on to still be alive. If the backend is killed
mid-command the node keeps running with whatever force it last had, so anything
that enforces a limit has to live down here, not up in Python.

> **Only part of that package is in this repository.** The driver node itself is
> Sathvik Kadimisetty's `falcon_ros2` (BIROMED-Lab, Basel), which this project
> forked and modified rather than wrote. It is not redistributed here. What is
> here is the part written for this project — see
> [`falcon_robot/ros2_ws/src/falcon_ros2/README.md`](falcon_robot/ros2_ws/src/falcon_ros2/README.md)
> for the full list and for what you need in order to build.

**The renderer.** `haptic_renderer.cpp` and its header were written for this
project. They wrap CHAI3D and turn a scene description into something the hand
can feel, using the finger-proxy algorithm so a solid cannot be pushed through
by shoving harder.

**The scene messages.** `HapticObject.msg` and `HapticScene.msg` were added for
rendering and are the vocabulary the model writes in. Publishing a scene
replaces whatever was rendered before; an empty one clears it.

**What the driver node does**, for context, since the halves only make sense
together: it opens the USB device and spins a thread against `drdWaitForTick()`.
Every tick it adds the impedance force arriving on `/force_command` to whatever
CHAI3D is rendering from the current scene, clamps the total to `max_force_n`,
drops it to zero unless a grip button is held, applies gravity compensation so
the handle does not sag, and publishes what it measured. The ceiling and the
deadman are the two things that must be there rather than in Python, for the
reason above.

## How it fits together

```
Claude / MCP ──► robot_control ──► backend.py (rclpy)
                     │  publishes /force_command  (impedance)   ┐
                     │  publishes /haptic_scene   (objects)      ├─► falcon_haptic_node (C++)
                     │  subscribes /device_state  (pos/vel/btn)  ┘        │ CHAI3D proxy @ 1 kHz
                     ▼                                                    ▼
                 viewer.py ──► RViz                            Novint Falcon (USB)
```

The node **owns the device** and runs the real-time loop; the Python backend only
speaks topics (so only one process ever opens the USB device). Impedance guidance
(target + stiffness) is computed in the backend and sent as `/force_command`;
object rendering is described in `/haptic_scene` and rendered by CHAI3D inside the
node. Both are summed and magnitude-clamped to 8 N.

## Install

`robot-control` first, because this package depends on it:

```bash
pip install -e ../robot-control
pip install -e .
python -m pytest -q            # 91 tests; without ROS the device-bound five skip
```

Installing this package is what makes this robot discoverable: the
`robot_control.robots` entry point in `pyproject.toml` is the whole registration
mechanism. There is no manifest to keep in sync, and nothing in `robot-control`
names a robot.

## Device setup

Everything below is this device's own: the core needs none of it, and a robot
that is not a Falcon needs none of it either. Needed only to drive the real
hardware — the tests run without any of it.

Requires a Novint Falcon, the **Force Dimension SDK**, and **CHAI3D**, on
Ubuntu 24.04 with ROS 2 Jazzy — and the `falcon_ros2` driver node, which is not
in this repository. Without it the Python side still imports, runs and tests;
only the hardware path is missing.

### 1. Force Dimension SDK

Download the Linux SDK from <https://www.forcedimension.com/software/sdk> and
install it so `libdhd` is discoverable:

```bash
sudo mkdir -p /opt/forcedimension
# extract the SDK into /opt/forcedimension (so /opt/forcedimension/{include,lib} exist)
# then the runtime symlinks and the config the build expects:
cd /opt/forcedimension/lib/release/lin-x86_64-gcc
ln -sf libdhd.so.3.* libdhd.so.3 && ln -sf libdhd.so.3 libdhd.so
ln -sf libdrd.so.3.* libdrd.so.3 && ln -sf libdrd.so.3 libdrd.so
# and drop the driver package's ForceDimensionSDKConfig.cmake into
# /opt/forcedimension/ so CMake can find libdhd and libdrd
```

Export these before building or running (add them to `~/.bashrc`):

```bash
export ForceDimensionSDK_DIR=/opt/forcedimension
export LD_LIBRARY_PATH=/opt/forcedimension/lib/release/lin-x86_64-gcc:$LD_LIBRARY_PATH
```

### 2. CHAI3D

Built once from source, statically:

```bash
git clone https://github.com/chai3d/chai3d.git deps/chai3d
cd deps/chai3d && mkdir -p build && cd build
cmake -DCMAKE_BUILD_TYPE=Release .. && make chai3d      # -> deps/chai3d/build/libchai3d.a
```

> **Pass `-DCHAI3D_ROOT`.** The driver package's `CMakeLists.txt` hard-codes a
> default path, so name yours outright:
> `colcon build --cmake-args -DCHAI3D_ROOT=$PWD/deps/chai3d`.

### 3. USB permissions

```bash
sudo groupadd -f force_dimension && sudo usermod -aG force_dimension $USER
sudo cp 11-forcedimension.rules /etc/udev/rules.d/   # ships with the driver package
sudo udevadm control --reload-rules && sudo udevadm trigger --action=add --subsystem-match=usb
# then replug the Falcon — the rule sets the device to mode 0666
```

### 4. Build the ROS 2 workspace

Drop the driver package into `falcon_robot/ros2_ws/src/falcon_ros2/`, add the
two files from this repository's `src/` and `msg/` to it, then:

```bash
source /opt/ros/jazzy/setup.bash
cd falcon_robot/ros2_ws && colcon build
```

## Adding another robot

A new repository, laid out like this one — three things and one entry point,
with no change to `robot-control` and none here. Note the module sits *inside*
the repository directory and is named after the distribution, not after the
directory, for the reason given at the top:

```
anyexo/                             the repository
└── anyexo_robot/                   the module: `import anyexo_robot`
    ├── spec.yaml                   parameters, bounds, rate caps,
    │                               screen_axes, requires_hardware
    ├── backend.py                  implements RobotBackend; declares BACKEND
    └── exercises/                  what this device offers: its mechanics,
                                    its bounds, and whatever viewer it ships
```

```toml
[project.entry-points."robot_control.robots"]
anyexo = "anyexo_robot"
```

Write the **spec first** and review that: it is the contract, and it is readable
without running anything. `backend.py` here is the part to read first, since it is the only place that
knows a device.

## Exercises belong to the robot

What a device can offer — the mechanics as well as the limits — is a property of
the device, so an exercise lives here in full. `robot-control` holds only the
contract, `robot_control.exercise`, and the runner that ticks it:

```python
from robot_control.exercise import Exercise, ExerciseSpec, load_exercise_spec

class ReachExercise(Exercise):
    ...                     # configure / reset / update / status / view

SPEC = load_exercise_spec(Path(__file__).parent / "reach.yaml")

def EXERCISE() -> ReachExercise:
    return ReachExercise(SPEC)
```

Offering the same exercise on a second device is a YAML with different numbers.
Rendering is an exercise too (`render`), so it starts, stops and e-stops like
everything else — and its object vocabulary is the robot's own, since what a
device can render is a property of the device.

## Running

```bash
falcon_robot/scripts/run_node.sh --require-button   # owns the USB device
falcon_robot/scripts/run_mcp.sh                     # what an MCP client starts
falcon_robot/exercises/haptic_rendering/run_rviz.sh   # RViz view of the scene
falcon_robot/exercises/reach/run_window.sh            # the reach window
```

The launchers resolve an interpreter that has both packages importable, through
`ROBOT_PYTHON`, then `.venv/` here, then `python3`. They have to name it
outright: **MCP clients spawn servers with a sanitised environment**, so an
activated virtualenv is not inherited. A launcher that cannot find a working
interpreter says so rather than dying as *"Connection closed"*.

After changing anything under `falcon_robot/ros2_ws/`, stop the node and
rebuild — a running node keeps executing the old binary:

```bash
cd falcon_robot/ros2_ws && colcon build --packages-select falcon_ros2
```

Only **one** process may hold the Falcon open at a time. `run_node.sh` owns the
device; everything else talks to it over ROS 2 topics.

## Control surface (what the AI can command)

- **Impedance guidance** — `set_parameters`: `target_x/y/z`, `stiffness`, `damping`.
- **Actions** — one-shot commands that are neither a setting nor an activity.
  This device has one, `release`: guidance to zero at once. `set_parameters`
  is held to one step per call in either direction, so falling from a firm
  hold to nothing takes several; `release` does it in one, and unlike
  `e_stop` it does not latch.
- **Exercises** — one `start_`/`configure_` pair each, from `falcon_robot/exercises/`:
  - `reach` — a dot appears, the user moves onto it and holds still;
  - `render` — a haptic scene, held steady, with objects:
    - solids: `sphere`, `box`, `cylinder`, `ellipsoid`, `cone`, and `mesh`
      (arbitrary AI-authored `vertices` + `triangles`) — rendered by the
      god-object proxy (no pop-through);
    - fields: `plane` (one-sided wall), `spring`, `viscous`;
    - `vibration` on its own — a cue felt wherever the hand is, with no
      geometry and no net push, capped low so it can never move the hand;
    - per-solid **texture**: `friction` (0–1), `vibration_freq`/`vibration_amp`.
  - `stop_exercise` ends whichever is running and clears the scene.
- **Safety** — `e_stop` (latching) / `resume`; forces clamped to 8 N, stiffness ≤ 3000 N/m.

## Notes / gotchas

- The node applies force only while a **grip button is held** unless launched with
  `require_button:=false` (a deadman switch). `robot://falcon/state` reports
  `status.button_pressed`.
- Haptic solids are felt by **approaching them**. If an object is spawned exactly
  around a stationary hand, the proxy cold-starts inside it and renders no force
  until the hand exits and re-enters.
- If `dhdOpen()` reports "no device found" with the device plugged in, another
  process is holding it, or the udev rule hasn't applied — replug and check
  `ls -l /dev/bus/usb/*/*` for mode `0666`.
